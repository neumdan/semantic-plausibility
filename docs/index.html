First Podman test — from zero

  1. Install Podman and podman-compose. On macOS/Windows initialise a machine once if needed, then start it. Run the remaining commands in this repository.
  2. Prepare settings and directories. Existing settings are preserved:
cp -n pipeline.example.toml pipeline.toml
cp -n .env.example .env
chmod 600 .env
mkdir -p ../input local output

The supplied TOML selects examples/laboratory.csv, MII Laboratory 2026.0.3 and real public endpoints. An older TOML retains its previous choices: inspect [input] and [lookups].

  1. Build the reusable runner, check configuration, then execute:
podman-compose build run-plausibility-check
podman-compose run --rm run-plausibility-check config-check
podman-compose run --rm run-plausibility-check check --out output/01-lookup.csv
  1. Open output/01-lookup.html. The synthetic input has 8 rows → 7 distinct review sets / 84 source occurrences. The findings depend on real service coverage; an unresolved set is a result, not an installation failure.
  2. For another run choose a fresh --out filename. Rebuild only after code/dependency updates. Keep reports with their sidecars.

config-check checks local configuration/files, not every remote service. Add --connections to probe selected APIs. Model probing is included only when research is enabled; verify the model separately below. Neither probe proves correct model answers.

B · Select the input and mapping

Data mapping and target specification are separate. Select the actual resource type, map source headers/columns, and select the guide to check towards. A guide cannot infer the meaning of unknown hospital columns. The runner writes CSV/HTML reports; FHIR/OMOP/CDS Hub output writers are not implemented.

B1 · CSV export — recommended starting point
  1. Put your export under ../input/ or local/. Start from the appropriate profile recipe below.
  2. Set input.type="csv" and the file path. Set granularity="individual" for rows with IDs, or "distinct" for already aggregated sets. Map a real count column only when its meaning is known.
  3. Edit [input.columns]: left side is our logical role; right side is your actual column name.
  4. Select output.mode="distinct" for grouped review or "items" to retain IDs from individual input. Run A1.
[input]

path = "../input/lab-export.csv"
granularity = "individual"

[input.columns]
source_id = "observation_id"
analyte_name = "test_name"
code = "test_code"
code_system = "test_code_system"
value = "numeric_result"
unit = "unit_label"
unit_code = "unit_code"
unit_system = "unit_system"
reference_ranges_json = "reference_ranges_json"

[output]
mode = "distinct"
path = "output/site-lab.csv"

This is a replacement input/output block, not another block to append. Each mapped column must exist. Preserve local LIS coding as local coding; do not relabel it LOINC to obtain a pass. All reference intervals and qualifiers belong in the reference JSON field. Field contract and aggregate statistics.

B4 · FHIR server, TORCH/CQL or LIS API
  1. Use the hospital's supported extraction tool: TORCH/CRTDL or its CQL workflow for FHIR; vendor export for LIS APIs.
  2. Select resource types, period/status/cohort and required linked Medication resources. Export the actual resources or sufficient scalar fields. A count-only MeasureReport is insufficient.
  3. Record the extraction criteria/manifest alongside the export. Transfer the export to the local review machine if needed.
  4. Use B1 for CSV or B3 for FHIR files; run the same A1–A3 checks.

Direct FHIR-server querying, Kafka/message interception and vendor LIS clients are not implemented here. The public terminology endpoint is never a source-patient server. MII/FDPG integration · CQL selection example.

MII SU-TermServ requires an authorised client certificate/key pair, configured as client_cert / client_key file paths. A bearer token alone is not its read-access setup. Certificate setup.

C4 · Combine local/API sources or work offline
  1. List actual canonical systems per source. Enable only intended sources.
  2. Use [terminology] strategy="fallback" for local-first lookup then compatible APIs. Use "all" to cross-check every enabled compatible source; conflicts remain unresolved.
  3. For disconnected checking, capture real responses in a connected run with output.lookup_pack, transfer that file and catalogues, then select network.mode="offline" and input.snapshot. Coverage is limited to the captured queries.

A network error or missing catalogue entry does not prove an invalid code. Reports retain attempted sources, returned editions and gaps. Full source configuration reference.

Prepare Ollama for A2 / A3

Default: ministral-3:3b, from Mistral's Apache-2.0 Ministral 3 family. The quantized download is about 3 GB. Start with 8 GiB available VM memory for this model; shared services need more. CPU-only inference in a macOS/Windows Podman VM can take minutes. This is a candidate generator/extractor, not a medically validated adjudicator.

  1. Keep these settings in the existing TOML model block:
[models.local]
runtime = "ollama"
base_url = "http://127.0.0.1:11434/v1"
container_base_url = "http://ollama:11434/v1"
model = "ministral-3:3b"
temperature = 0
max_tokens = 2048
timeout_seconds = 600
response_mode = "json_schema"
  1. Start the service, install the selected model and real unit catalogue, then verify the available model:
podman-compose --profile research up -d ollama
podman-compose --profile research run --rm model-init
podman-compose --profile research run --rm catalog-init
podman-compose --profile research exec -T ollama ollama list
podman-compose run --rm run-plausibility-check config-check --connections
  1. Run A2 or A3 using the original A1 report. model-init proves model availability; the AI report/trace shows successful, failed or rejected inference calls.
  2. Stop inference when finished; weights remain:
podman-compose --profile research stop ollama

Persistent storage: manual and scripted examples use the same SQC_OLLAMA_VOLUME from .env, default semantic-plausibility-ollama. To reuse an existing store, find it with podman volume ls and set that exact name before starting. Use one service at a time for the same store. Do not use down --volumes or volume pruning to save image space.

Port already in use? Set SQC_OLLAMA_PORT=11435 in .env, then start again. Containers still use http://ollama:11434/v1. Native Python then needs base_url="http://127.0.0.1:11435/v1". Alternatively use native Ollama via the documented host address instead of another server. Native Ollama / LM Studio.

Model weights download once; inference and reports stay local. Public retrieval receives terminology/search terms, not patient IDs or local measured values/reference bounds. Prompts and responses are auditable in .trace.jsonl.

Read the report

Configuration and methods at the top records A–D choices, input path/table/mapping, configured defaults, profile, sources, selected model/research scope and output. It excludes credentials and connection strings. Expand How this item was assessed beside each set for its accounting, methods, assumptions, lookup attempts/editions and next improvement step. The CSV column assessment_context_json contains the same item record; the summary contains shared run_context.

Enabled services are listed separately from actual item evidence. AI records distinguish inherited A1 results from new recommendations, and show new model/research activity; cached evidence can be reused. Full FHIR validation is a run-level result unless independently attributed to the item. Old archived reports remain unchanged; rerun for these new fields.

  1. Source set: check the code, names, units, values/ranges, context and source counts were read correctly.
  2. Linked data: inspect canonical name/LOINC axes, lookup source and edition. A membership pass does not establish the correct analyte selection.
  3. Proposal: review suggested code/name/unit, explanation, required transformation and evidence. No verified factor means no executable unit transformation.
  4. Coverage/gaps: inspect unknown/unavailable evidence, conflicting sources, reference applicability and optional FHIR outcomes. Numeric readiness is not MII certification.

Laboratory CSV exposes lookup_attempts_json; medication uses sources_json and, where present, ddd_references_json. AI adds source_data_json, linked_data_json, recommendation_set_json and quoted evidence. Sources are shown beside the sets in HTML. HTML previews at most 2,000 rows; CSV retains all rows.

Retain the CSV, HTML, summary, evidence and audit together; AI adds its trace. Verify integrity:

podman-compose run --rm run-plausibility-check verify /app/output/01-lookup.audit.jsonl

For a rerun change --out, then point research --report at that new A1 CSV. Existing reports are protected. --log-level DEBUG gives more progress; INFO/WARNING/ERROR are available. Logs avoid credentials and clinical values; the audit remains active.
