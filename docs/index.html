Laboratory semantic plausibility

Populate the selected MII KDS Observation with defensible codes, names, values, units and reference context. Check the source set, research reported practice, obtain clinician decisions and reuse approved mappings within their scope.

Goal and scope

The complete laboratory set is code + code system/edition + name + value/bounds + unit + unit system + all reference intervals/context. Source validity is checked before proposing target coding. The clinician evaluates semantic correctness using definitions and evidence of practice.

The default examples load the real MII Laboratory 2026.0.3 snapshot. LOINC is a preferred code binding; UCUM is fixed for quantitative value units. Profiles define requirements; the operator configures the real services and credentials. Requirements and later medication/diagnosis/procedure adapters.

The output is a mapping plan and review dossier. Approved transformations are applied in institutional ETL; full FHIR validation checks actual individual resources. Aggregate statistics do not become patient Observations.

1. Prepare once and choose a runtime

cp -n pipeline.example.toml pipeline.toml
cp -n .env.example .env
mkdir -p ../input local output

pipeline.toml is the default for all three runtimes. Keep the supplied input for the first check. TOML holds pipeline settings; .env holds credentials and optional container settings. No shell exports are needed.

Python with uv

uv run --no-sync --env-file .env run-plausibility-check --config pipeline.toml

The direct script is equivalent: uv run --no-sync --env-file .env python run-plausibility-check.py --config pipeline.toml.

Docker Compose

Podman with podman-compose

B · Configure API and credentials

The default NLM/public FHIR APIs require no credentials. For the official LOINC API, replace the existing lookups.loinc table:

[lookups.loinc]
enabled = true
type = "loinc"
endpoint = "https://fhir.loinc.org"
username_env = "LOINC_FHIR_USERNAME"
password_env = "LOINC_FHIR_PASSWORD"

Set these two credential values in ignored .env, or use username_file/password_file pointing to local/secrets/. Generic FHIR APIs use token_env/token_file; WHO uses client ID/secret references. Keep one dedicated LOINC and one UCUM service active.

Local German labels can complement API checks. For an offline run set network.mode="offline" and reference actual captured UCUM/LOINC evidence via input.snapshot. BfArM translation supplements provide labels; they cannot alone validate every UCUM expression or establish conversion factors. Missing evidence remains unverified, with no fallback to an unconfigured API.

4. What runs

  1. Check headers, types and source-frequency contract.
  2. Validate actual FHIR documents locally against the pinned guide with Matchbox/HL7 or the MII validator; retain OperationOutcomes before grouping.
  3. Group complete guarded sets in DuckDB; compute eligible distributions.
  4. Verify units with NLM and codes/example units with the configured FHIR terminology service; optionally compare supplied names with sourced aliases.
  5. Check semantic fit, verified conversion factors, numeric values and supplied reference bounds.
  6. Write the checked export; a separate evidence command retrieves exactly verified alternatives and quoted page/PubMed/Europe PMC evidence.
  7. Write separate findings and proposals; source values stay unchanged.

5. Read the report

Open output/laboratory-review.html; the CSV contains each grouped set, separate checks, source evidence and transformation proposals. The table reads source set → linked terminology → complete proposal, including code/system/edition, analyte/component, canonical name, unit, value/bound transformations and reference evidence. Each proposal shows its source, edition and available hash/quote. Missing context or factors stay unresolved. Formal FHIR validation has its own section and OperationOutcome link. The summary contains returned terminology editions, coverage, timing and lookup failures; the audit records artifact hashes.

StatusMeaning
passedAssessed checks supported
suggestionDocumented proposal requires approval
unclearSource/context/evidence unavailable or interpretation ambiguous

Additional fields: canonical_name, suggested_code, suggested_name, suggestion_state and reference_candidates_json. Model-selected candidates retain exact lookup evidence and review requirements. Source checks and approved_mapping_ready remain separate from original numeric readiness.

An out-of-reference value is descriptive, not a patient diagnosis. Readiness measures numeric/terminology completeness, not MII certification or clinical approval. Physicians review proposals in a separate CSV copy. For another run choose a new output path or explicitly set overwrite=true.

7. Research with Ollama and Europe PMC

Use the same pipeline.toml. The check is deterministic; research-evidence explicitly enables the second pass on its audited CSV and sidecars. Set research.scope="studies", sources=["europe_pmc","pubmed"], and a local model. Europe PMC needs no API key. Native inference uses models.local.base_url="http://127.0.0.1:11434/v1"; Compose uses container_base_url="http://ollama:11434/v1".

Podman: setup once, then execute
podman-compose --profile research up -d ollama
podman-compose --profile research run --rm --build model-init

# If no check report exists yet:
podman-compose run --rm --build run-plausibility-check
podman-compose --profile research run --rm research-evidence

Start the Podman machine in your terminal first on macOS/Windows. Skip model/catalogue setup when already provisioned. For Docker replace podman-compose with docker compose.

Python: inspect and run using native Ollama
uv run --no-sync research-evidence --config pipeline.toml --plan
uv run --no-sync --env-file .env research-evidence --config pipeline.toml

Native Ollama must be running with the configured model; see model/catalogue setup.

Open output/laboratory-review.research.html for the complete sourced proposals. The matching CSV has source_data_json, linked_data_json and recommendation_set_json. The trace records actual searches, prompts and guarded replies; the research section reports accepted model calls. Use --out with a fresh prefix to repeat research. --report is optional and defaults to TOML output.path.

The pipeline retrieves real LOINC pages and Europe PMC/PubMed abstracts. The starter maps its analyte names from source_test. Exact LOINC part lookups resolve the analyte and measurement axes; alternative codes are exactly verified before model selection. An optional research.europe_pmc.QUERY_FILTER restricts public searches, while unsupported reference intervals stay missing. The model selects exactly verified code/name candidates or extracts supported quotes; it cannot independently invent a verified mapping or clinical interval. Local values/reference bounds and IDs stay out of searches/prompts. Tasks, safeguards and concrete cases · BfArM downloads beside the repository.

Example: a verified hemoglobin code can supply its full canonical name; g/L → g/dL with factor 0.1 applies independently to each bound. A local code or malformed unit remains a clinician-reviewed candidate until source meaning/context and conversion are established.

Validate FHIR resources with the guide

Matchbox includes the official HL7 FHIR validator. The same TOML pins the MII Laboratory profile and complete package. validator-init prepares the server configuration; the connected build installs the guide and dependencies. Validation runs locally before grouping actual FHIR documents.

podman-compose --profile validation run --rm --build validator-init
podman-compose --profile validation up -d blaze
podman-compose --profile validation run --rm terminology-init
podman-compose --profile validation up -d --build matchbox

For Docker use docker compose. Enable validation.enabled=true for FHIR input. CSV/DB aggregates remain semantic-set inputs. The HTML reports formal validation separately and links the original OperationOutcomes. Add reader links to MII/FHIR/GitHub in [specification.links]; actual validation uses the pinned package/snapshot. Configure links and artifacts.

The complete example has a required OBI identifier/assigner, two laboratory category codings, subject/time and UCUM Quantity. Its invalid variant removes the identifier while leaving the numeric semantic set intact. Run both examples, select the MII backend and configure VM memory.

8. Reuse clinician reviews

Return the original tuple_id with review_decision, reviewer/time/evidence and approved code/name/unit/factor. Import a minimal review CSV or edit only review columns in a copy:

uv run --no-sync --env-file .env run-plausibility-check review-import --config pipeline.toml --report output/laboratory-review.csv --review local/clinician-review.csv --registry local/clinician-mappings.json

Set input.source_namespace before collecting reviews, then enable the registry and run a fresh check:

[quality]
review_registry = "local/clinician-mappings.json"

Reuse is limited to the same source/site, complete tuple context, local catalogue fingerprint and profile edition/rules. Targets and transformations are rechecked. Rejected, deferred or revoked decisions never become executable mappings. The registry retains reviewer, evidence and history; model weights and source records remain unchanged.

Example: 140 g/L with illustrative bounds 120–160 g/L can have a verified factor 0.1 to g/dL; each bound is transformed in its own unit. An already coded g/dL bound uses factor 1. Local/typo interpretations are explicitly clinician-declared rather than labelled as verified source conversions.
